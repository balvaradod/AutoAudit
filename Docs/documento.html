1. Descripción del proyecto

AutoAudit es un sistema hecho en PostgreSQL que guarda los cambios (insert, update y delete) que se hacen en las tablas de una base de datos. El administrador escoge qué tablas, qué columnas y qué eventos quiere vigilar, y el sistema crea solo los triggers necesarios. Cada cambio se guarda en una tabla llamada bitacora con el valor anterior, el valor nuevo, el usuario, la fecha y la IP de donde se hizo.

Incluye una interfaz web (Python y Flask) para configurar y consultar. Todo el sistema vive en un esquema llamado auditoria, así no se mezcla con las tablas del usuario.

2. Diagrama entidad-relación

Relaciones

  • Una tabla auditada tiene muchas columnas auditadas (1 a N).
  • Una columna auditada puede tener varias configuraciones, una por cada evento (INSERT, UPDATE, DELETE).
  • La configuración une una columna con un evento y dice si está activa. Es la que indica qué evento se registra cuando cambia una columna de una tabla.
  • Cada registro de la bitácora apunta a la configuración que se usó, al usuario que hizo el cambio y a la estación de trabajo desde donde lo hizo.
  • La bitácora no tiene llave foránea hacia la tabla original. Esto es a propósito, para que los datos queden guardados aunque el registro se borre.

4. Manual de configuración y activación de auditoría

Se debe entrar con un usuario que sea superusuario o miembro del rol auditoria_admin.

Paso 1. Ver qué tablas y columnas hay

SELECT * FROM auditoria.vw_tablas_disponibles;
SELECT * FROM auditoria.vw_columnas_disponibles WHERE nombre_tabla = 'cliente';

Paso 2. Activar la auditoría de una tabla

Forma rápida (configura y crea el trigger):

SELECT auditoria.auditar_tabla('public', 'cliente',
       ARRAY['nombre','correo','saldo'],
       ARRAY['INSERT','UPDATE','DELETE']);

Si no se mandan columnas se auditan todas; si no se mandan eventos se usan los tres.

Forma paso a paso:

SELECT auditoria.agregar_configuracion('public', 'cliente', 'saldo', 'UPDATE');
SELECT auditoria.generar_trigger('public', 'cliente');

Paso 3. Cambiar la configuración

Después de cualquier cambio hay que volver a generar el trigger:

SELECT auditoria.desactivar_configuracion('public', 'cliente', 'correo', 'UPDATE');
SELECT auditoria.generar_trigger('public', 'cliente');

Paso 4. Quitar la auditoría de una tabla

SELECT auditoria.quitar_trigger('public', 'cliente');

Paso 5. Consultar el historial

SELECT * FROM auditoria.historial_por_usuario('postgres');
SELECT * FROM auditoria.historial_por_usuario('postgres', '2026-10-01', '2026-10-31');
SELECT * FROM auditoria.historial_por_columna('public', 'cliente', 'saldo');

Paso 6. Exportar a CSV

psql -d mi_bd -v usuario=postgres -v esquema=public -v tabla=cliente -v columna=saldo -f sql/09_exportar.sql

Reglas que valida el sistema

  • La tabla y la columna deben existir (se revisa contra el diccionario de datos).
  • El evento solo puede ser INSERT, UPDATE o DELETE.
  • La tabla debe tener llave primaria.
  • Solo administradores pueden configurar.
  • Cada trigger pertenece a una sola tabla (trg_audit_esquema_tabla).
  • Las configuraciones no se borran, se desactivan, porque la bitácora las referencia.

5. Instalación y despliegue de triggers

Requisitos

Ubuntu 26.04 LTS y PostgreSQL 18 (se probó también en PostgreSQL 16). Se necesita un usuario con permisos para crear bases de datos.

sudo apt install postgresql
sudo -u postgres psql

Instalación

git clone https://github.com/balvaradod/AutoAudit.git
cd AutoAudit
chmod +x instalar.sh
./instalar.sh autoaudit_bd

El script instalar.sh se ejecuta con el usuario normal (sin poner sudo adelante); por dentro usa sudo para entrar como el usuario postgres. Crea la base y ejecuta en orden:

ArchivoContenido
01_estructura.sqlEsquema, tablas, índices, rol y seguridad
02_diccionario.sqlConsultas al diccionario de datos
03_configuracion.sqlFunciones de configuración
04_generador_triggers.sqlGenerador dinámico de triggers
05_consultas.sqlConsultas de historial
06_datos_prueba.sqlTabla de ejemplo (cliente)
07_pruebas.sqlPruebas funcionales
08_rendimiento.sqlPrueba de rendimiento
09_exportar.sqlExportar reportes a CSV

Para correr los ejemplos y las pruebas:

cat sql/06_datos_prueba.sql sql/07_pruebas.sql | sudo -u postgres psql -d autoaudit_bd
cat sql/08_rendimiento.sql | sudo -u postgres psql -d autoaudit_bd

Despliegue de un trigger

Cuando se ejecuta generar_trigger el sistema: (1) valida que la tabla exista y tenga llave primaria, (2) lee las configuraciones activas, (3) arma el código de una función en PL/pgSQL con un bloque por cada columna y evento, (4) crea la función con EXECUTE, (5) borra el trigger anterior si había y crea un trigger AFTER FOR EACH ROW solo con los eventos configurados. Si algo falla se muestra un error con el nombre de la tabla. La función devuelve el código SQL que generó.

Ejemplo del trigger generado:

CREATE TRIGGER trg_audit_public_cliente AFTER INSERT OR UPDATE OR DELETE
ON public.cliente FOR EACH ROW
EXECUTE FUNCTION auditoria.fn_audit_public_cliente();

Seguridad

  • Solo auditoria_admin o superusuarios pueden configurar (se revisa con validar_admin()).
  • Se le quitaron todos los permisos al público sobre el esquema; ningún usuario normal puede hacer INSERT en la bitácora. Solo las funciones de los triggers (SECURITY DEFINER) escriben.
  • Un trigger BEFORE UPDATE/DELETE en la bitácora lanza error, para que no se pueda modificar ni borrar.
  • La IP es un dato personal; se debe usar solo para auditoría y restringir quién consulta la bitácora (solo auditoria_admin tiene SELECT).

6. Interfaz web

Para configurar la auditoría y consultar el historial sin escribir SQL se hizo una interfaz web con Python (Flask). Está en la carpeta interfaz/ y usa las mismas funciones y vistas SQL de los scripts; no tiene lógica de auditoría propia.

Pantallas

PantallaQué hace
Iniciar sesiónEntra con un usuario y contraseña de PostgreSQL. Así la base de datos revisa si es administrador y los cambios quedan a nombre de ese usuario.
Configurar auditoríaLista las tablas del diccionario de datos, muestra sus columnas con casillas por INSERT, UPDATE y DELETE, y al guardar genera el trigger y muestra el código SQL creado. También permite desactivar la auditoría de la tabla.
Configuración actualMuestra qué tablas tienen trigger, con qué columnas y eventos.
HistorialBusca cambios por usuario o por columna, con fechas opcionales, en orden cronológico, y los exporta a CSV.

Instalación en Ubuntu

Primero se debe tener instalada la base de datos (sección 5). Luego:

sudo -u postgres psql -c "ALTER USER postgres PASSWORD 'una_clave';"
sudo apt install python3 python3-venv
cd AutoAudit/interfaz
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python3 app.py

Después se abre http://localhost:5000 en el navegador. Datos de entrada: servidor localhost, puerto 5432, base autoaudit_bd, usuario postgres y la contraseña que se puso arriba. Para cerrar el programa se presiona Ctrl+C en la terminal.

Un usuario que no sea administrador puede iniciar sesión pero PostgreSQL le niega los permisos y la pantalla muestra el error.

Prueba de rendimiento

Se insertaron filas en una tabla de 3 columnas, primero sin auditoría y luego auditando 2 columnas (INSERT, UPDATE, DELETE). Resultados en una máquina virtual de pruebas:

Filas insertadasSin auditoría (seg)Con auditoría (seg)Veces más lento
1,0000.0020.05326.5
10,0000.0150.49432.9
50,0000.0832.65432.0
100,0000.1625.03731.1

Conclusiones: el tiempo crece de forma lineal con el número de filas, o sea que no empeora con el volumen. El costo es de aproximadamente 0.05 milisegundos por fila auditada, que para operaciones normales (una o pocas filas) no se nota. En cargas masivas sí se nota, porque por cada fila se escriben varias filas en la bitácora (una por columna). Con 322,010 filas en la bitácora, la consulta del historial de un usuario tardó alrededor de 1.4 segundos.
